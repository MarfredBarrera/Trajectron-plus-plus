# Demo drivable map — handoff

A 2D **drivable / non-drivable** raster of the Unity `Demo` scene, for use as a Trajectron++
`GeometricMap` and for visualization. Generated by the Unity Editor tool
**Tools ▸ Map Export ▸ Occupancy Map Exporter** (`Assets/Scripts/Editor/OccupancyMapExporter.cs`).

## Files

| File | What it is |
|------|------------|
| `Demo_drivable.png`  | Grayscale raster. **Drivable = white (255), non-drivable = black (0).** |
| `Demo_drivable.json` | Metadata + the 3×3 **world→pixel homography**. |
| `Demo_drivable.yaml` | ROS `map_server` descriptor (for viewing in rviz2). |

"Drivable" = the ground-truth `TaxiwayLane` network: each lane centerline inflated to a lane
width, connected turns/junctions bridged via the lane graph, then a morphological closing pass
to seal parallel-lane seams. It is **not** obstacle-occupancy — an empty non-lane apron reads as
non-drivable.

## Coordinate frame (read this first)

The raster is registered to the **same ROS-world frame your trajectories use**
(`GroundTruthPublisher` / `bag_to_nuscenes.py`), via the fixed Unity→ROS axis swap:

```
ROS x =  Unity z        ROS y = -Unity x
```

The 2D world plane is `(rx, ry) = (Unity z, -Unity x)`, in **meters**. Any node position you feed
Trajectron++ must be in this same `(rx, ry)` frame — then the map and the trajectories line up
with no extra transform.

## This export's parameters

| Field | Value |
|-------|-------|
| Resolution | **0.1 m/px** (= 10 px/m) |
| Size | 2443 × 6399 px  (≈ 244 m × 640 m) |
| Lane width | 8 m |
| Bridged connections | yes |
| Closing radius | 4 px |
| World bounds (ROS) | x ∈ [44.09, 288.36], y ∈ [−264.66, 375.21] |
| Homography (world→px) | `[[10, 0, −440.9175], [0, −10, 3752.14868], [0, 0, 1]]` |

The homography maps `(rx, ry, 1) → (col, row)` in PNG pixel coordinates (top-left origin, y-down;
PNG row 0 = `ry_max`):

```
col = 10·rx − 440.9175
row = −10·ry + 3752.14868
```

## Load into Trajectron++

Trajectron++ `GeometricMap(data, homography, description)` wants `data` shaped **`[layers, x, y]`**
(x is the *first* spatial axis) and a homography mapping world → `(x_pixel, y_pixel) = (col, row)`.
Our JSON homography is already `(rx, ry) → (col, row)`, so `data` must be `[col, row]` — i.e. the
image transposed.

```python
import json
import numpy as np
from PIL import Image
from environment import GeometricMap   # Trajectron++ environment/map.py

def load_drivable_map(png_path, json_path):
    meta = json.load(open(json_path))
    img = np.asarray(Image.open(png_path).convert("L"))    # (H, W), 0/255, drivable=255

    # GeometricMap.data is [layers, x, y]; homography maps world->(col,row).
    # Image is [row, col] -> transpose to [col, row] to match the axis order.
    layer = img.T                                          # (W, H): layer[col,row] = img[row,col]
    data  = layer[np.newaxis, :, :].astype(np.uint8)       # (1, W, H)

    H = np.array(meta["homography_world_to_px"], dtype=float)
    return GeometricMap(data=data, homography=H, description=f"drivable:{meta['scene']}")
```

Attach it (the Demo map is static, so one shared object serves every `Scene`):

```python
gmap = load_drivable_map("Demo_drivable.png", "Demo_drivable.json")
for scene in scenes:
    scene.map = {"VEHICLE": gmap, "PEDESTRIAN": gmap, "VISUALIZATION": gmap}
```

Only node types listed in your config's `map_encoder` actually consume the map (usually `VEHICLE`).

## Config knobs

1. **`map_channels: 1`** in the `map_encoder` block — this map has a single drivable layer
   (the stock nuScenes config uses 3). Only the first conv's `in_channels` changes.

2. **Scale vs. patch size.** The homography bakes in **10 px/m**. The stock nuScenes config assumes
   **3 px/m** with `patch_size [50,10,50,90]` (~33 m of context); at 10 px/m those same pixel counts
   cover only ~10 m and cost ~11× the pixels. Either:
   - **Recommended:** re-export at `resolution = 0.3333` (→ 3 px/m) and reuse the stock `patch_size`
     unchanged. Keep this fine 0.1 m/px map for visualization only.
   - Or keep 10 px/m and scale `patch_size` ~3.3× to preserve real-world coverage (heavier compute).

## Sanity check before training

Overlay a real recorded trajectory (meters, ROS `(rx, ry)` frame). It should sit on the white
drivable ribbon:

```python
import matplotlib.pyplot as plt
gmap = load_drivable_map("Demo_drivable.png", "Demo_drivable.json")
plt.imshow(gmap.data[0].T, origin="upper", cmap="gray")   # back to [row, col] for display
mp = gmap.to_map_points(traj_xy)                           # traj_xy: (N,2) -> (col, row)
plt.scatter(mp[:, 0], mp[:, 1], s=4, c="r")
plt.show()
```

## Viewing in rviz2

`Demo_drivable.yaml` is a standard `map_server` descriptor (origin at the lower-left corner
`(rx_min, ry_min)`, drivable = free/light). Serve it with `nav2_map_server` and add a `Map` display
on the `map` frame.

## Regenerating

Open the `Demo` scene in Unity → **Tools ▸ Map Export ▸ Occupancy Map Exporter** →
**Auto-compute bounds from lane network** → adjust *Lane width* / *Fill gaps* if needed →
**Export drivable map**. Output lands in `<UnityProject>/map_exports/<Scene>/`. The same tool works
on the other scenes (`Urban_crossing`, `Emergency_response`, …).
